METHODOLOGY (stated honestly — read this before the findings)

The historical P1-G4 methodology drove a real Tauri window on Windows via
scripts/windows-webview-proof.ps1 and captured hashed PNG files. On this macOS
box, in this sandboxed session, I hit two real environment limits attempting
the equivalent:

1. Native screen capture (`screencapture`) failed outright: "could not create
   image from display" — Screen Recording permission is not granted to this
   sandboxed process, and I cannot grant it myself (it requires a GUI click in
   System Settings that only the operator can make). `osascript`/System Events
   also lacks Accessibility access ("-1719").
2. A DOM-to-canvas fallback (serialize the live DOM into an SVG data URL via
   foreignObject, draw it to a <canvas>, export via toDataURL) reliably
   produced a rendered image internally but the canvas was marked "tainted"
   and refused export — a known Chromium behavior with foreignObject+blob-URL
   SVGs, independent of whether the content is actually cross-origin. I tried
   this both with and without the app's raster logo image; both tainted.
3. Playwright MCP (which screenshots via CDP, not OS-level capture, and would
   have sidestepped both issues) requires a browser-extension bridge that is
   not installed in this environment.

None of these are fixable from inside this session without operator action
(granting Screen Recording permission, or installing the Playwright bridge
extension). Rather than claim a hashed-file capture I do not actually have, or
silently skip verification, I did the next-best thing available to me:

I built and ran the ACTUAL compiled app (not a mockup) and verified its real,
live-rendered DOM against every design decision from tonight's session,
programmatically where possible (exact pixel measurements, not eyeballing),
and visually via the Browser pane's screenshot tool (which renders inline for
review in this session, though it did not yield a hashable file on disk
either — same underlying permission gap).

   — CARGO_TARGET_DIR was confirmed unset beforehand; the binary landed in
   this worktree's own fresh target/debug/kaydence, untouched by and
   untouching the canonical checkout.

3. Launched the compiled binary directly (`./target/debug/kaydence`,
   confirmed no other kaydence process running first, per the P1-G3

   for the duration of this check — no repeat of the P1-G3 <600s termination
   symptom during this short interactive session (this is not a P1-G3

4. Because native screenshot capture was unavailable (see above), I pivoted

ONE REAL FINDING FROM THIS VERIFICATION (not previously caught — the mockups
were never tested at a narrower width): at browser-pane widths below the
app's designed 900px default, the status bar's pill group wraps to a second
row, and the mic-level meter's centering (margin-left/right:auto, which
assumes a single row) degrades to "pushed to the row's end" rather than
staying centered, because there is nothing after it on that row to balance
against once pills wrap away. This is NOT visible at the app's actual
900x600 default size (confirmed equidistant there) but WOULD show up if a
user shrinks the window meaningfully narrower, since tauri.conf.json marks
the window resizable. Flagging as a minor, non-blocking follow-up — not
something this signoff should hold open for, but worth a small responsive
fix later (e.g. drop the meter, or let pills scroll instead of wrap, below
some width threshold).
